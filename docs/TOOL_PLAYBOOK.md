# 도구 제작 플레이북

새 도구를 만들거나 기존 도구를 개선할 때의 **기준서**다. `tests/registry.test.ts`와 `scripts/check-dist.mjs`가 이 문서의 기계적으로 검사 가능한 부분을 강제하고, 나머지는 사람과 리뷰 에이전트(`.claude/agents/tool-reviewer.md`)가 확인한다.

---

## 1. 무엇을 만들까 (선정)

`docs/CATALOG.md`에서 우선순위가 가장 높은 `todo` 항목을 고른다. 새 아이디어는 다음 조건을 모두 만족해야 한다.

- **검색 수요가 있다.** 사람들이 실제로 검색하는 말(예: "resize image", "글자수 세기", "5 minute timer")이 있어야 한다.
- **클라이언트에서 완결된다.** 서버나 외부 API 없이 브라우저만으로 동작해야 한다.
- **하나의 의도다.** "이미지 도구"가 아니라 "이미지 크기 조절" 수준으로 쪼갠다. 의도가 다르면 별도 도구로 만든다.
- **기존 도구와 겹치지 않는다.** 겹치면 새 도구 대신 기존 도구의 variant나 기능으로 넣는다.

## 2. 경쟁 조사와 Edge 정하기 (생략 금지)

1. 주요 로케일(최소 en, ko)에서 **핵심 키워드로 검색해 상위 3개 도구를 실제로 열어 본다.** 웹 검색과 페이지 열람 도구를 쓴다.
2. 각 도구에서 다음을 기록한다.
   - 업로드가 필요한지(서버 처리인지)
   - 광고, 팝업, 대기 화면, 가입 유도가 있는지
   - 사용 제한(파일 수, 크기, 일일 횟수)이 있는지
   - 클릭 수: 결과를 얻기까지 몇 번 클릭하는지
   - 빠진 기능, 부정확한 결과, 모바일 UX 문제
   - **그들이 우리보다 잘하는 점**(정직하게)
3. 이 기록을 `meta.competitors[]`에 `{ name, url, weakness }`로 남긴다. weakness는 "광고가 있음" 같은 일반론이 아니라 확인한 구체적 사실로 쓴다. 그들의 강점은 `(Strength: …)`로 덧붙인다.
4. **Edge를 정한다.** 아래 중 우리가 _실제로_ 더 나은 축을 `meta.edges`에 넣는다. 페이지 상단 배지로 노출되므로, 사실이 아니면 넣지 않는다.

| EdgeKind      | 넣을 수 있는 조건                                                                   |
| ------------- | ----------------------------------------------------------------------------------- |
| `privacy`     | 파일이나 텍스트가 기기 밖으로 나가지 않음 (경쟁 도구는 업로드함)                    |
| `no-ads`      | 경쟁 상위 도구에 광고가 있음                                                        |
| `performance` | 업로드나 대기가 없어서 체감 속도가 확실히 빠름                                      |
| `usability`   | 클릭 수 감소, 키보드 단축키, 붙여넣기, 자동 저장 등                                 |
| `design`      | 큰 글씨, 정돈된 레이아웃, 모바일 최적화가 눈에 띄게 나음                            |
| `features`    | 경쟁 도구에 없거나 유료인 기능이 있음 (구체적으로 무엇인지 경쟁사 기록에 명시)      |
| `accuracy`    | 계산이나 처리 결과가 더 정확함 (예: CJK 단어 분절, 백그라운드 탭 타이머 오차)       |
| `offline`     | 로딩 후 오프라인 동작 (모든 클라이언트 도구는 기본으로 해당하므로 강조할 때만 넣음) |
| `no-signup`   | 경쟁 도구가 가입이나 로그인을 요구하거나 사용량을 제한함                            |

**Edge를 하나도 찾지 못하면 그 도구는 만들지 않는다.** 대신 CATALOG에 이유를 남긴다.

## 3. 구현

### 파일 구성

`npm run new-tool -- <slug> <category>`로 만들어지는 파일들의 역할은 다음과 같다.

| 파일               | 규칙                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `meta.ts`          | slug는 영어 kebab-case, 핵심 영어 키워드(`image-resizer`, `word-counter`). **런칭 후 변경 금지.**                     |
| `logic.ts`         | 순수 함수만 둔다. DOM, Preact, `window` 금지. 계산, 파싱, 포맷팅은 모두 여기에 둔다.                                  |
| `logic.test.ts`    | 정상 케이스, 경계값(0, 빈 문자열, 최대값), 유니코드(한글, 이모지, CJK), 이전에 고친 버그를 다룬다.                    |
| `Tool.tsx`         | 상태와 UI만 담당한다. `src/components/ui` 프리미티브로 조립한다. 문자열은 전부 `ui` prop에서 가져온다(하드코딩 금지). |
| 브라우저 전용 처리 | Canvas, File 등은 `Tool.tsx`에 섞지 말고 별도 파일(예: `resize.ts`)로 분리한다.                                       |
| `Island.astro`     | 수정하지 않는다.                                                                                                      |

### UX 규칙

- **결과까지 최소 클릭.** 입력하면 즉시 결과를 보여 준다. "변환" 버튼을 누르게 하지 않는다. 무거운 처리는 debounce한다.
- **합리적 기본값.** 페이지를 열자마자 그대로 써도 되는 값으로 시작한다(예: 타이머 5분, 리사이즈 1080px).
- **입력 방법을 모두 지원한다.** 파일은 드래그, 클릭, 붙여넣기(Ctrl/⌘+V)를 모두 받는다(`Dropzone`이 처리). 텍스트는 붙여넣기 즉시 처리한다.
- **상태 보존.** 사용자가 공들여 입력한 것(텍스트, 설정)은 `safeStorage`로 저장해 새로고침해도 유지한다. 키 형식은 `tools:<slug>:<name>`이다.
- **키보드.** 모든 조작이 Tab과 Enter로 가능해야 한다. 자주 쓰는 동작에는 단축키를 두고 `<Kbd>`로 안내한다. 입력 필드에서 타이핑 중일 때는 단축키를 무시한다.
- **오류는 친절하게.** 읽을 수 없는 파일이나 잘못된 입력은 해당 위치에 `Notice tone="danger"` 또는 인라인 문구로 알린다. 콘솔 에러만 남기고 조용히 실패하지 않는다.
- **성능.** 페이지 JS는 150KB(raw) 이하로 유지한다. 큰 라이브러리(PDF, 압축 코덱 등)는 사용자가 실제로 쓰는 순간 `await import()`로 로드한다.

### Variants (프리셋 랜딩 페이지)

검색 수요가 큰 구체적 변형(예: "5 minute timer", "resize image to 1080x1080")은 `meta.variants`로 별도 URL을 만든다.

- `preset`은 도구 초기 상태를 **실제로** 바꿔야 한다(테스트로 강제됨). 문구만 다른 페이지는 금지한다.
- `intro`는 숫자만 바꾼 템플릿이 아니라 그 변형에 맞는 구체적 용도를 담는다(`timer/meta.ts`의 `USES` 참고).
- 근거 없이 수십 개를 만들지 않는다. 실제로 검색되는 변형만 만든다.

## 4. 콘텐츠 (SEO + GEO)

도구 페이지는 **도구가 먼저, 설명은 아래**에 둔다. 콘텐츠는 사용자가 실제로 궁금해할 정보만 담는다.

| 필드          | 규칙                                                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`       | 핵심 키워드로 시작하고, 30~60자(ko는 더 짧아도 됨)로 쓴다. 형식은 `<키워드> — <차별점/부가 키워드>`. 사이트명은 레이아웃이 자동으로 붙인다. |
| `description` | 검색 의도에 바로 답하고 edge를 언급한다. 90~160자. 도구 간에 중복되면 안 된다.                                                              |
| `h1`          | 사람들이 검색하는 자연스러운 이름(예: "Image Resizer", "글자수 세기").                                                                      |
| `tagline`     | H1 아래 한 문장. 무엇을 어떻게 더 잘하는지.                                                                                                 |
| `keywords`    | 사이트 내 검색용 동의어와 다른 표현. meta keywords로 쓰지 않는다.                                                                           |
| `howTo`       | 3~6단계. 명령형으로, 실제 UI 라벨과 일치하게 쓴다.                                                                                          |
| `sections`    | 2~4개. **구체적 정보**(공식, 규격 수치, 한계, 팁, 근거 출처)를 담는다. 일반론이나 키워드 반복은 금지한다.                                   |
| `faq`         | 3~8개. 사람들이 실제로 검색하는 질문을 쓴다. 답변은 **질문 없이 읽어도 완결되는 문장**으로 쓴다(LLM이 그대로 인용함). 수치를 포함한다.      |
| `ui`          | 컴포넌트 안의 모든 문자열. 짧고 동사 중심으로.                                                                                              |

### 로케일별 작성

- 번역이 아니라 **현지화**다. 해당 언어 사용자가 실제로 쓰는 검색어와 단위, 관행을 반영한다(한국어: 자소서, 평, 원, 만 나이 등).
- 수치나 규격이 나라마다 다르면 그 로케일에 맞는 것을 쓴다(예: 용지 크기 A4 vs Letter).
- 어색한 직역 대신 그 언어로 처음부터 썼을 법한 문장으로 쓴다.

### 사실 확인

규격(SNS 이미지 크기, 글자 제한 등), 공식, 연구 수치는 작성 시점에 확인한다. 출처가 있으면 본문에 짧게 밝힌다(예: "Brysbaert, 2019"). 변할 수 있는 규격을 쓴 도구는 `meta.updated`로 갱신 시점을 관리한다.

## 5. 검증

```bash
npm run verify
```

그다음 `npm run dev`로 직접 사용해 본다.

1. 기본값 그대로 바로 쓸 수 있는가?
2. 375px 모바일에서 가로 스크롤 없이 쓸 수 있는가?
3. 다크모드에서 대비와 가독성은 괜찮은가?
4. 키보드만으로 끝까지 쓸 수 있는가?
5. 경쟁 도구와 나란히 놓고 봤을 때 edge가 **체감되는가?**

가능하면 리뷰 에이전트를 돌린다: "tool-reviewer 에이전트로 `<slug>` 리뷰해줘".

## 6. 마무리

- `docs/CATALOG.md`에서 상태를 `live`로 바꾼다.
